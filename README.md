# Seekio

Video I/O for AI agents.

Seekio is a Remote MCP server that lets AI agents progressively
inspect video timelines as timestamped image frames.

```text
Video
  ↓
Seekio
  ↓ timestamped image frames
Coding Agent
  ↓ vision + reasoning
Repository investigation / fix
```

> Seekio does not understand video. It lets AI agents understand video.

## What is Seekio?

Seekio gives a coding agent (Claude Code, Codex, or any MCP client) a way to
look at a screen recording over time. You upload a video, the agent inspects
the whole timeline coarsely, narrows in on the suspicious range, and finally
pulls the exact frame it needs. The main use case is frontend debugging:
"the drawer jumps to the left for a split second around 3s, find out why."

Seekio itself does no video understanding, no inference, and no storage of its
own. Cloudflare Stream stores and encodes the video; Seekio turns timestamps
into JPEG frames and hands them to the agent as MCP image content.

## Architecture

```text
Claude Code / Codex / MCP Client
              │
              │ Streamable HTTP
              ▼
┌──────────────────────────────┐
│ Seekio Worker                │
│ GET  /health                 │
│ POST /mcp                    │
│                              │
│ video_create_upload          │
│ video_import_url             │
│ video_info                   │
│ video_overview               │
│ video_frames                 │
│ video_frame                  │
│ video_delete                 │
└──────────────┬───────────────┘
               │ Stream binding
               ▼
┌──────────────────────────────┐
│ Cloudflare Stream            │
│ upload / store / encode      │
│ metadata / thumbnails/delete │
└──────────────────────────────┘
```

- Stateless Remote MCP server on Cloudflare Workers (`createMcpHandler` from the Agents SDK, MCP SDK v2).
- Video bytes never pass through the Worker: the client uploads directly to Cloudflare Stream through a one-time upload URL (`video_create_upload`), or Stream downloads a public file URL itself (`video_import_url`).
- Frames are Stream on-demand thumbnails fetched with a signed token and returned as base64 `image/jpeg` content.
- No database, no Durable Objects, no R2. Videos are temporary artifacts: you delete them with `video_delete`, and an hourly Cron Trigger deletes any Seekio video older than the retention (24 hours by default).

## Requirements

- A Cloudflare account with a [Stream](https://developers.cloudflare.com/stream/) subscription (Stream is a paid product).
- Node.js 24, [mise](https://mise.jdx.dev/), and pnpm (installed by mise).
- Wrangler login (`pnpm wrangler login`) for local development and manual deploys.

## Cloudflare Stream setup

1. Enable Stream on your Cloudflare account.
2. Seekio uses the Workers **Stream binding** (`stream.binding = "STREAM"` in `wrangler.jsonc`). No API token is needed at runtime; the binding is authorised by the deployment.
3. Every video is created with `requireSignedURLs = true`, so raw video ids never expose playable URLs. Frames are fetched with a short-lived token generated by the binding.

Local development uses `"remote": true` on the binding, so `mise run dev` talks to the real Stream service through your Wrangler login.

The Images binding is also `"remote": true`: even under `mise run dev`, `region` crops use the real Cloudflare Images service and consume the free tier (5,000 unique transformations per month).

## Deploy

### Manual

```bash
mise run deploy       # runs check, then wrangler deploy
pnpm wrangler secret put SEEKIO_AUTH_TOKEN
```

### Continuous deployment with Workers Builds

Production deploys use the Cloudflare Workers GitHub integration, so no
deployment credentials live in GitHub Actions.

1. In the Cloudflare dashboard open **Workers & Pages** → **Create** → **Import a repository** and pick this repository (or connect it from the existing `seekio` Worker's **Settings** → **Builds**).
2. Build settings:
   - Build command: `pnpm install --frozen-lockfile`
   - Deploy command: `pnpm wrangler deploy`
   - Production branch: `main`
3. Add secrets (`SEEKIO_AUTH_TOKEN`) and any Access vars under the Worker's **Settings** → **Variables and Secrets**.

GitHub Actions (`.github/workflows/ci.yml`) runs `mise run check` on every pull request and push to `main`; it never deploys. Make the `check` job a required status check in branch protection.

## Tool reference

All tools return JSON or text in `text` content; frames are `image` content (`image/jpeg`, base64). Errors come back as `isError: true` with `[CODE] message`, where the message tells the agent what to do next (for example `[TOO_MANY_FRAMES] Requested 16 frames, but Seekio allows at most 15 frames per call. Narrow the interval or reduce fps.`).

### `video_create_upload`

| Input | Type | Notes |
| --- | --- | --- |
| `filename` | string, optional | Stored as metadata |
| `max_duration_seconds` | integer, optional | 1 to the server limit (default 300) |

```json
{
  "video_id": "abc123",
  "upload_url": "https://upload.cloudflarestream.com/...",
  "upload_command": "curl -sS --fail-with-body -X POST -F 'file=@\"<PATH>\"' 'https://upload.cloudflarestream.com/...'",
  "expires_at": "2026-01-01T00:15:00.000Z",
  "max_duration_seconds": 300,
  "max_upload_bytes": 209715200,
  "auto_delete_after_hours": 24
}
```

The server cannot read local files, so uploading is a separate step: replace `<PATH>` in `upload_command` with the local file path and run it in a shell, then call `video_info` with `wait_seconds` until `ready`. `upload_command` is equivalent to `POST upload_url` as `multipart/form-data` (field `file`), which must happen before `expires_at` (15 minutes by default). Uploads over 200 MB are not supported in v1.

`<PATH>` sits inside a single-quoted shell string and a double-quoted curl filename (`-F 'file=@"<PATH>"'`), so paths with spaces, `;`, `,`, `$` or backticks work as they are. Inside `<PATH>`, escape every `"` and `\` with a backslash, and do not use a single quote `'` in the path (copy the file to another path first). `--fail-with-body` needs curl 7.76 or newer.

### `video_import_url`

Imports a video from a public URL that serves a video file directly (for example `https://example.com/foo.mp4`). Web pages such as YouTube are not supported. Cloudflare Stream downloads the file asynchronously, so call `video_info` with `wait_seconds` until `ready`.

| Input | Type | Notes |
| --- | --- | --- |
| `url` | string | `http` or `https` only |
| `filename` | string, optional | 1 to 255 characters, stored as metadata |

```json
{ "video_id": "abc123", "status": "downloading", "auto_delete_after_hours": 24 }
```

The duration limit cannot be enforced up front for imports: once the video is `ready`, frame tools reject it with `[VIDEO_TOO_LONG]` when it exceeds the limit, and the message tells the agent to `video_delete` it. Related errors: `[INVALID_URL]` (not a publicly reachable direct video file), `[URL_ALREADY_IMPORTED]` (Stream already has this URL), `[UPLOAD_CREATE_FAILED]` (file too large, quota reached, rate limited, or other Stream failure). URLs are never written to logs.

### `video_info`

| Input | Type |
| --- | --- |
| `video_id` | string | |
| `wait_seconds` | integer, optional | 0 to 25. Omit or `0` to check once. Otherwise waits (polling every 2 s) until the video is `ready` or `error`, or the time is up, and returns the latest state; running out of time is not an error, so call again if it is still processing |

```json
{ "id": "abc123", "status": "ready", "duration": 14.82, "width": 1179, "height": 2556, "ready": true }
```

`delete_after` (ISO time, creation time plus the retention) tells when the automatic cleanup will consider the video expired; it is omitted when Stream does not report a creation time. While the video is encoding, `pct_complete` (0 to 100) is included when Stream reports it; the field is omitted otherwise.

`status` is one of `pendingupload`, `downloading`, `queued`, `inprogress`, `ready`, `error`. Frame tools refuse to run until `ready` is `true`:

```text
[VIDEO_NOT_READY] Video is still processing. Call video_info again before requesting frames.
```

### `video_overview`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `max_frames` | integer, optional | Default 12, max 15 |
| `interval_seconds` | number, optional | Fixed spacing; omit to spread `max_frames` evenly. Returns `TOO_MANY_FRAMES` if covering the video would need more than `max_frames` |

Returns a summary line followed by `Frame at <t>s` / image pairs in timestamp order. Timestamps are `i * duration / (N - 1)`, clamped to just before the end of the video, with duplicates removed for very short videos.

### `video_frames`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `start` | number | seconds, `>= 0` |
| `end` | number | seconds, `> start`, `<= duration` |
| `fps` | number, optional | Default 5, max 30 |

Timestamps are `start + index / fps` (no floating point accumulation). At most 15 frames per call; Seekio never lowers `fps` on its own, it returns `TOO_MANY_FRAMES` instead.

### `video_frame`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `at` | number | seconds, `0 <= at < duration`, millisecond precision |
| `region` | object, optional | `{ x, y, width, height }` as ratios (0-1) of the frame. Origin is the top-left corner: `x` is the left edge, `y` is the top edge. `x + width <= 1` and `y + height <= 1`, `width` and `height` `> 0`. Example: the bottom credits are `{ "x": 0, "y": 0.8, "width": 1, "height": 0.2 }` |

Returns `Frame at 3.347s` followed by one image (whole frames are capped at 720px tall).

With `region`, Seekio fetches the frame at the source video's resolution and crops the rectangle through the Cloudflare Images binding, so small text (credits, captions) stays readable. The result is a JPEG whose long edge is at most 1568px (shrunk if larger, never enlarged), and the caption reports the crop, e.g. `Frame at 3.347s, region x=0 y=0.8 w=1 h=0.2 (1568x176 px)`. Errors: `INVALID_REGION` (bad values), `REGION_UNAVAILABLE` (the Worker has no `IMAGES` binding), `REGION_CROP_FAILED` (the Images transformation failed, for example because the free tier of 5,000 unique transformations per month is exhausted). In the last two cases call `video_frame` again without `region`, or wait and retry. `region` is only available on `video_frame`.

### `video_delete`

| Input | Type |
| --- | --- |
| `video_id` | string |

```json
{ "video_id": "abc123", "deleted": true }
```

Deleting an already deleted video succeeds. Call it as soon as you are done: automatic deletion (see [Data handling](#data-handling)) is a backstop, not a substitute.

## Example debugging workflow

User: "Around 3 seconds the drawer flashes to the left for a moment. Find the cause and fix it." (with a screen recording attached)

1. The agent calls `video_create_upload` (or `video_import_url` for a public file URL), uploads the recording, and calls `video_info` with `wait_seconds` until `ready`.
2. `video_overview` returns 12 frames across the 14.8 s clip; the drawer looks wrong only in the frame at 2.7 s.
3. `video_frames` with `start: 2.4, end: 3.6, fps: 20` (25 frames) shows the drawer briefly rendered at `translateX(-100%)` for two frames before the open transition starts.
4. `video_frame` at `2.95` confirms the exact intermediate state.
5. The agent searches the repository for the drawer transition, finds the missing initial transform on the mounted element, fixes it, and re-records to verify.
6. `video_delete` removes the recording.

The server instructions embedded in Seekio steer agents toward this progressive pattern: whole video → suspicious range → higher-FPS range → exact frame.

### When you already know the time

The progressive pattern is for videos you have not seen. If you already know when to look (for example the on-screen text or credits at a specific second), skip `video_overview`: call `video_info` (with `wait_seconds`) to confirm the video is `ready`, then call `video_frame` with `at`, or `video_frames` with a narrow `start` / `end` range around that time.

### Reading small text

Whole-frame images are downscaled, so fine print such as end credits can be unreadable. Call `video_frame` with `region` to crop just that area from the original-resolution frame, e.g. `{ "at": 12.3, "region": { "x": 0, "y": 0.8, "width": 1, "height": 0.2 } }` for the bottom 20%.

## Limits

| Limit | Default | Where |
| --- | --- | --- |
| Upload size | 200 MB | Stream direct upload (v1 does not support tus) |
| Video duration | 300 s | `MAX_VIDEO_DURATION_SECONDS` var (enforced by Stream for `video_create_upload`; checked after processing for `video_import_url`, where longer videos fail with `VIDEO_TOO_LONG`) |
| Upload URL lifetime | 900 s | `UPLOAD_URL_TTL_SECONDS` var |
| Video retention | 24 h | `VIDEO_RETENTION_HOURS` var (hourly Cron Trigger in `wrangler.jsonc`; a video can outlive it by up to about an hour) |
| Overview frames | 12 (max 15) | `src/config.ts` |
| Frames per `video_frames` call | 15 | `src/config.ts` (kept within MCP clients' output limits: 30 frames at 720p exceeded Claude Code's 25,000-token cap) |
| Max fps | 30 | `src/config.ts` |
| Frame height | min(source height, 720 px); never upscaled | `src/config.ts` |
| Concurrent frame fetches | 6 | `src/config.ts` |

## Optional MCP Server Portal integration

Seekio works without a portal. If you use a
[Cloudflare MCP Server Portal](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/),
`mise run portal` registers Seekio in it idempotently (create the portal itself
in the dashboard first; when created through the API the portal hostname also
needs a proxied CNAME to `gateway.agents.cloudflare.com`).

```bash
export CLOUDFLARE_ACCOUNT_ID=...
export CLOUDFLARE_API_TOKEN=...          # Access: MCP servers and portals write permission
export SEEKIO_MCP_URL=https://seekio.example.workers.dev/mcp
export SEEKIO_PORTAL_ID=...
export SEEKIO_PORTAL_SERVER_ID=seekio    # optional, default "seekio"
export SEEKIO_AUTH_TOKEN=...             # optional: registers the server with bearer auth
export SEEKIO_PORTAL_AUTH=oauth          # optional: oauth | bearer | unauthenticated

mise run portal:dry-run   # show changes only
mise run portal           # apply
```

The script creates the MCP server entry if missing, updates it when the URL or auth type drifts, syncs its tool list, and ensures the portal mapping exposes all seven tools without aliases. Running it twice is a no-op. Worker deploys (`mise run deploy`) never touch the portal.

`SEEKIO_PORTAL_AUTH` selects the server's `auth_type`. When unset, it is `bearer` if `SEEKIO_AUTH_TOKEN` is set and `unauthenticated` otherwise. `bearer` requires `SEEKIO_AUTH_TOKEN`; `oauth` never sends a token. Use `oauth` when the Worker is protected by Cloudflare Access with Managed OAuth.

## Data handling

Seekio does not keep your video on your machine: a video you upload or import is stored in your Cloudflare account (Cloudflare Stream) until it is deleted. Do not use Seekio for material that must not leave your machine or be stored in that account, even temporarily.

- **Where it lives**: the video is stored in Cloudflare Stream in the account that runs Seekio, and Stream encodes it there. Seekio itself stores nothing (no database, no R2).
- **Viewing**: videos are created with `requireSignedURLs = true`, so they can be viewed only through signed URLs. Seekio generates them for frame requests; anyone with the account's Stream access can still see the videos.
- **Video bytes skip the Worker**: the client uploads straight to Stream's one-time upload URL, or Stream downloads a public file URL itself (`video_import_url`). Frames returned to the agent (base64 JPEG) do pass through the Worker in memory and are sent to the MCP client, but are not stored.
- **Logs**: signed URLs, upload URLs, tokens, `Authorization` headers, and frame bytes are never logged. Logs contain event names, video ids, counts, and durations.
- **Automatic deletion**: an hourly Cron Trigger deletes every video Seekio created (Stream `meta.application = "seekio"`; videos whose `meta.application` is not `seekio` are never touched) that is older than `VIDEO_RETENTION_HOURS` (24 by default). Because it runs hourly, a video can remain up to about an hour longer. The cleanup needs the Worker to be deployed with the `triggers.crons` entry in `wrangler.jsonc`; if it is removed, nothing deletes videos except `video_delete` and the backstop below.
- **Backstop**: each video is also created with a Stream `scheduledDeletion` 31 days out (Stream does not accept less than 30 days), so it is removed by Stream itself even if the cleanup never runs.
- **Immediate deletion**: call `video_delete` when you are done.

## Security

- See [Data handling](#data-handling) for where videos are stored and when they are deleted.
- Stream videos are created with `requireSignedURLs = true`; frames are fetched with tokens from the Stream binding, and tokens, upload URLs, and Authorization headers are never logged.
- `video_id` is not treated as a secret, and v1 has no per-user ownership: run Seekio as a single trust domain internal tool.
- `/mcp` has two optional authentication layers, enforced together when both are set:
  - **Static bearer token**: set the `SEEKIO_AUTH_TOKEN` secret; clients send `Authorization: Bearer <token>`.
  - **Cloudflare Access JWT**: set `CF_ACCESS_TEAM_DOMAIN` (for example `myteam.cloudflareaccess.com`) and `CF_ACCESS_AUD` (the Access application's AUD tag); Seekio validates the `Cf-Access-Jwt-Assertion` header against your team's public keys, issuer, audience, and expiry.
- **Warning**: with neither layer configured, `/mcp` is open to anyone who knows the URL, and every `video_create_upload` consumes your Stream quota.
- If MCP clients reach Seekio through Access's managed OAuth (for example a Claude Desktop connector), the `Authorization` header carries the Access token, so do not set `SEEKIO_AUTH_TOKEN` in that deployment; rely on the Access JWT layer. Service tokens (`CF-Access-Client-Id` / `CF-Access-Client-Secret` headers) combine with the bearer token without conflict.
- `/health` is unauthenticated and returns only the server name and version.
