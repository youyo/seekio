# Seekio

Video I/O for AI agents.

Seekio is a Remote MCP server that lets AI agents progressively
inspect video timelines as timestamped image frames.

```text
Video
  ↓
Seekio
  ↓ timestamped image frames
Coding Agent
  ↓ vision + reasoning
Repository investigation / fix
```

> Seekio does not understand video. It lets AI agents understand video.

## What is Seekio?

Seekio gives a coding agent (Claude Code, Codex, or any MCP client) a way to
look at a screen recording over time. You upload a video, the agent inspects
the whole timeline coarsely, narrows in on the suspicious range, and finally
pulls the exact frame it needs. The main use case is frontend debugging:
"the drawer jumps to the left for a split second around 3s, find out why."

Seekio itself does no video understanding, no inference, and no storage of its
own. Cloudflare Stream stores and encodes the video; Seekio turns timestamps
into JPEG frames and hands them to the agent as MCP image content.

## Architecture

```text
Claude Code / Codex / MCP Client
              │
              │ Streamable HTTP
              ▼
┌──────────────────────────────┐
│ Seekio Worker                │
│ GET  /health                 │
│ POST /mcp                    │
│                              │
│ video_create_upload          │
│ video_info                   │
│ video_overview               │
│ video_frames                 │
│ video_frame                  │
│ video_delete                 │
└──────────────┬───────────────┘
               │ Stream binding
               ▼
┌──────────────────────────────┐
│ Cloudflare Stream            │
│ upload / store / encode      │
│ metadata / thumbnails/delete │
└──────────────────────────────┘
```

- Stateless Remote MCP server on Cloudflare Workers (`createMcpHandler` from the Agents SDK, MCP SDK v2).
- Video bytes go directly from the client to Cloudflare Stream through a one-time upload URL; they never pass through the Worker.
- Frames are Stream on-demand thumbnails fetched with a signed token and returned as base64 `image/jpeg` content.
- No database, no Durable Objects, no R2. Videos are temporary artifacts that you delete with `video_delete`.

## Requirements

- A Cloudflare account with a [Stream](https://developers.cloudflare.com/stream/) subscription (Stream is a paid product).
- Node.js 24, [mise](https://mise.jdx.dev/), and pnpm (installed by mise).
- Wrangler login (`pnpm wrangler login`) for local development and manual deploys.

## Cloudflare Stream setup

1. Enable Stream on your Cloudflare account.
2. Seekio uses the Workers **Stream binding** (`stream.binding = "STREAM"` in `wrangler.jsonc`). No API token is needed at runtime; the binding is authorised by the deployment.
3. Every video is created with `requireSignedURLs = true`, so raw video ids never expose playable URLs. Frames are fetched with a short-lived token generated by the binding.

Local development uses `"remote": true` on the binding, so `mise run dev` talks to the real Stream service through your Wrangler login.

## Deploy

### Manual

```bash
mise run deploy       # runs check, then wrangler deploy
pnpm wrangler secret put SEEKIO_AUTH_TOKEN
```

### Continuous deployment with Workers Builds

Production deploys use the Cloudflare Workers GitHub integration, so no
deployment credentials live in GitHub Actions.

1. In the Cloudflare dashboard open **Workers & Pages** → **Create** → **Import a repository** and pick this repository (or connect it from the existing `seekio` Worker's **Settings** → **Builds**).
2. Build settings:
   - Build command: `pnpm install --frozen-lockfile`
   - Deploy command: `pnpm wrangler deploy`
   - Production branch: `main`
3. Add secrets (`SEEKIO_AUTH_TOKEN`) and any Access vars under the Worker's **Settings** → **Variables and Secrets**.

GitHub Actions (`.github/workflows/ci.yml`) runs `mise run check` on every pull request and push to `main`; it never deploys. Make the `check` job a required status check in branch protection.

## MCP client configuration

The endpoint is `https://<worker>.<account>.workers.dev/mcp`. Replace it with your custom domain if you route one to the Worker.

### Claude Code

```bash
claude mcp add --transport http seekio https://seekio.example.workers.dev/mcp \
  --header "Authorization: Bearer ${SEEKIO_AUTH_TOKEN}"
```

### Codex

`~/.codex/config.toml`:

```toml
[mcp_servers.seekio]
url = "https://seekio.example.workers.dev/mcp"
http_headers = { Authorization = "Bearer <token>" }
```

### Claude Desktop

Claude Desktop connects to remote servers through `mcp-remote` in `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "seekio": {
      "command": "npx",
      "args": [
        "-y", "mcp-remote", "https://seekio.example.workers.dev/mcp",
        "--header", "Authorization: Bearer <token>"
      ]
    }
  }
}
```

### Behind Cloudflare Access with a service token

Add the Access headers next to the bearer token (both layers are enforced when both are configured):

```bash
claude mcp add --transport http seekio https://seekio.example.workers.dev/mcp \
  --header "Authorization: Bearer ${SEEKIO_AUTH_TOKEN}" \
  --header "CF-Access-Client-Id: ${CF_ACCESS_CLIENT_ID}" \
  --header "CF-Access-Client-Secret: ${CF_ACCESS_CLIENT_SECRET}"
```

## Tool reference

All tools return JSON or text in `text` content; frames are `image` content (`image/jpeg`, base64). Errors come back as `isError: true` with `[CODE] message`, where the message tells the agent what to do next (for example `[TOO_MANY_FRAMES] Requested 61 frames, but Seekio allows at most 30 frames per call. Narrow the interval or reduce fps.`).

### `video_create_upload`

| Input | Type | Notes |
| --- | --- | --- |
| `filename` | string, optional | Stored as metadata |
| `max_duration_seconds` | integer, optional | 1 to the server limit (default 300) |

```json
{
  "video_id": "abc123",
  "upload_url": "https://upload.cloudflarestream.com/...",
  "expires_at": "2026-01-01T00:15:00.000Z",
  "max_duration_seconds": 300,
  "max_upload_bytes": 209715200
}
```

Upload the file with `POST upload_url` as `multipart/form-data` (field `file`) before `expires_at` (15 minutes by default). Uploads over 200 MB are not supported in v1.

### `video_info`

| Input | Type |
| --- | --- |
| `video_id` | string |

```json
{ "id": "abc123", "status": "ready", "duration": 14.82, "width": 1179, "height": 2556, "ready": true }
```

`status` is one of `pendingupload`, `downloading`, `queued`, `inprogress`, `ready`, `error`. Frame tools refuse to run until `ready` is `true`:

```text
[VIDEO_NOT_READY] Video is still processing. Call video_info again before requesting frames.
```

### `video_overview`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `max_frames` | integer, optional | Default 12, max 30 |
| `interval_seconds` | number, optional | Fixed spacing; omit to spread `max_frames` evenly. Returns `TOO_MANY_FRAMES` if covering the video would need more than `max_frames` |

Returns a summary line followed by `Frame at <t>s` / image pairs in timestamp order. Timestamps are `i * duration / (N - 1)`, clamped to just before the end of the video, with duplicates removed for very short videos.

### `video_frames`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `start` | number | seconds, `>= 0` |
| `end` | number | seconds, `> start`, `<= duration` |
| `fps` | number, optional | Default 5, max 30 |

Timestamps are `start + index / fps` (no floating point accumulation). At most 30 frames per call; Seekio never lowers `fps` on its own, it returns `TOO_MANY_FRAMES` instead.

### `video_frame`

| Input | Type | Notes |
| --- | --- | --- |
| `video_id` | string | |
| `at` | number | seconds, `0 <= at < duration`, millisecond precision |

Returns `Frame at 3.347s` followed by one image.

### `video_delete`

| Input | Type |
| --- | --- |
| `video_id` | string |

```json
{ "video_id": "abc123", "deleted": true }
```

Deleting an already deleted video succeeds.

## Example debugging workflow

User: "Around 3 seconds the drawer flashes to the left for a moment. Find the cause and fix it." (with a screen recording attached)

1. The agent calls `video_create_upload`, uploads the recording, and polls `video_info` until `ready`.
2. `video_overview` returns 12 frames across the 14.8 s clip; the drawer looks wrong only in the frame at 2.7 s.
3. `video_frames` with `start: 2.4, end: 3.6, fps: 20` (25 frames) shows the drawer briefly rendered at `translateX(-100%)` for two frames before the open transition starts.
4. `video_frame` at `2.95` confirms the exact intermediate state.
5. The agent searches the repository for the drawer transition, finds the missing initial transform on the mounted element, fixes it, and re-records to verify.
6. `video_delete` removes the recording.

The server instructions embedded in Seekio steer agents toward this progressive pattern: whole video → suspicious range → higher-FPS range → exact frame.

## Limits

| Limit | Default | Where |
| --- | --- | --- |
| Upload size | 200 MB | Stream direct upload (v1 does not support tus) |
| Video duration | 300 s | `MAX_VIDEO_DURATION_SECONDS` var |
| Upload URL lifetime | 900 s | `UPLOAD_URL_TTL_SECONDS` var |
| Overview frames | 12 (max 30) | `src/config.ts` |
| Frames per `video_frames` call | 30 | `src/config.ts` |
| Max fps | 30 | `src/config.ts` |
| Frame height | 1080 px | `src/config.ts` |
| Concurrent frame fetches | 6 | `src/config.ts` |

## Optional MCP Server Portal integration

Seekio works without a portal. If you use a
[Cloudflare MCP Server Portal](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/),
`mise run portal` registers Seekio in it idempotently (create the portal itself
in the dashboard first; when created through the API the portal hostname also
needs a proxied CNAME to `gateway.agents.cloudflare.com`).

```bash
export CLOUDFLARE_ACCOUNT_ID=...
export CLOUDFLARE_API_TOKEN=...          # Access: MCP servers and portals write permission
export SEEKIO_MCP_URL=https://seekio.example.workers.dev/mcp
export SEEKIO_PORTAL_ID=...
export SEEKIO_PORTAL_SERVER_ID=seekio    # optional, default "seekio"
export SEEKIO_AUTH_TOKEN=...             # optional: registers the server with bearer auth

mise run portal:dry-run   # show changes only
mise run portal           # apply
```

The script creates the MCP server entry if missing, updates it when the URL or auth type drifts, syncs its tool list, and ensures the portal mapping exposes all six tools without aliases. Running it twice is a no-op. Worker deploys (`mise run deploy`) never touch the portal.

## Security

- Stream videos are created with `requireSignedURLs = true`; frames are fetched with tokens from the Stream binding, and tokens, upload URLs, and Authorization headers are never logged.
- `video_id` is not treated as a secret, and v1 has no per-user ownership: run Seekio as a single trust domain internal tool.
- `/mcp` has two optional authentication layers, enforced together when both are set:
  - **Static bearer token**: set the `SEEKIO_AUTH_TOKEN` secret; clients send `Authorization: Bearer <token>`.
  - **Cloudflare Access JWT**: set `CF_ACCESS_TEAM_DOMAIN` (for example `myteam.cloudflareaccess.com`) and `CF_ACCESS_AUD` (the Access application's AUD tag); Seekio validates the `Cf-Access-Jwt-Assertion` header against your team's public keys, issuer, audience, and expiry.
- **Warning**: with neither layer configured, `/mcp` is open to anyone who knows the URL, and every `video_create_upload` consumes your Stream quota.
- If MCP clients reach Seekio through Access's managed OAuth (for example a Claude Desktop connector), the `Authorization` header carries the Access token, so do not set `SEEKIO_AUTH_TOKEN` in that deployment; rely on the Access JWT layer. Service tokens (`CF-Access-Client-Id` / `CF-Access-Client-Secret` headers) combine with the bearer token without conflict.
- `/health` is unauthenticated and returns only the server name and version.
